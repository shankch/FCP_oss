I wrote `design.yaml`, `frame.md` and `requirements.yaml` for `fib4(n)`, and `fcp lint` reports clean. Each cycle after the reset cycle is one call. `n` is a 6-bit input, so the trace covers n from 0 to 63; larger values and negative numbers are not part of the trace, since the request sets no upper limit and signals are unsigned. The returned value goes on a 57-bit `result` signal. The largest value in that range, fib4(63) = 132,419,948,094,134,672, is just under 2^57. Running Python and `bc` needed approval, so I worked that number out by hand and checked it two different ways. `outcome` is 2 bits with `raises: []`: 0 means it returned an integer that fits, 1 means any exception or no answer, and 2 means it returned anything else. There is one frame rule, F-ZERO (`outcome != 0 -> result == 0`), backed by R-FR-1 in `requirements.yaml`, a definition quoting `frame.md` with its line number set by `fcp anchor`; I then deleted `draft.yaml`. The scope tries every n from 0 to 63 and also lists 0 to 7, the values the request mentions. I named the design `review` to match the `requirements.yaml` that was already there, rather than following the examples' `code_*` names. One thing for whoever formalizes this: the doctests in `spec.md` (fib4(5) = 0, fib4(6) = 0, fib4(7) = 2) don't match the recurrence it defines, which gives 4, 8 and 14. As instructed, the frame doesn't mention this, but 57 bits is wide enough for either version.
