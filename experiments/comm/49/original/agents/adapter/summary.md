I wrote `design.yaml` and `frame.md` for `modp(n, p)`, and `fcp lint` reports no errors ("lint: clean"). Each cycle after the reset in cycle 0 is one call with no memory between calls. The inputs `n` and `p` are 16-bit signals, so each takes 0 to 65,535. That covers every value in the doctests (n up to 1101, p up to 101) and the ones just past them, and leaves room for the large exponents behind "be aware of numerics". The returned value is a 16-bit `result`, and `outcome` is 2 bits: 0 it returned an integer that fits, 1 it raised any exception or didn't finish (`raises: []`, since the request names no exception), 2 it returned anything else. The `function` section declares `modp` with two `int` arguments and an `int` return. Its scope tests n densely from 0 to 1200 plus 65,535 and 400 random values, and p densely from 0 to 120 plus 40 random values; the doctest constants and their neighbours are added automatically. `frame.md` explains the calls, the inputs, the outputs and the outcome codes, says that negative or larger arguments aren't part of the trace, and states one frame rule, F-ZERO (`result` is 0 unless `outcome` is 0). That rule cites R-FR-1 in `requirements.yaml`, a definition quoting frame.md, with `lines: [38]` computed by `fcp anchor` from `draft.yaml`, which I left in the workspace. One thing for whoever formalizes this: FCP-PL's `%` only accepts a constant divisor, so 2^n mod p with p as an input can't be written directly. I described the interface only and left that problem to the formalizer.
