I wrote `design.yaml`, `frame.md` and `requirements.yaml` for `simplify(x, n)`, and `fcp lint` reports "lint: clean". The two arguments `x` and `n` are each a string signal of up to 8 characters, with character codes 0–255. The returned boolean is on the 1-bit `result`. The 2-bit `outcome` reads 0 for a returned True/False, 1 for any exception or no answer, and 2 for any other return; `raises` is `[]` because the request names no exception. The request puts no limit on the numbers in the fractions, so the 8-character limit is my choice: it fits the examples, values just outside the format and numbers of about six digits. A larger limit would cover more but makes the strings harder to formalize, and longer calls are outside the trace, which `frame.md` says. `frame.md` also says that signals are unsigned, that negative integers are not part of the trace, and that each argument is carried as its raw characters with no number read from them. The `function` section declares both arguments as `type: str`. Its `scope` uses the alphabet `0123456789/`, 2000 random strings per argument, and the fractions from the request's examples. There are two frame rules, each backed by a FRAME definition anchored to its line in `frame.md` with `fcp anchor`. F-ZERO (R-FR-1, line 52) says `result` is false unless `outcome` is 0. F-CODE (R-FR-2, line 53) says `outcome` is never 3; the examples have no such rule, but I added it because code 3 is unused when no exception is named. I named the design `review` to match the existing `requirements.yaml`, and left the `draft.yaml` used for anchoring in the workspace.
