I wrote `design.yaml`, `frame.md` and `requirements.yaml` for `sort_array(array)`, and `fcp lint` reports **clean**. In `design.yaml`, the argument is the input signal `array`, a list of at most 8 numbers from 0 to 255 each (width 8, length 8). The returned list is the output signal `result`, the same shape. There's also a 2-bit `outcome` coded as in the examples: 0 means it returned a list that fits, 1 means any exception or no answer, and 2 means it returned anything else. `raises` is `[]` because the request names no exception. The request puts no limit on list length or element size, so those bounds are my choice. Its examples go up to 7 elements and values up to 6, so 8 and 255 cover them plus the values just past them; you can raise either if you want. The `function` section declares `array` as `type: list` and the return as a list, with a scope built from the request's four example arrays, a set of elements (0–7, 254, 255) and 3000 random lists. The frame has one rule, F-EMPTY (`outcome != 0 -> len(result) == 0`). It cites R-FR-1, a definition quoting `frame.md` at line 51, which `fcp anchor` added to `requirements.yaml`. `frame.md` explains calls, lists and how they read in FCP-PL, the input and output tables and that rule. It says lists longer than 8, elements above 255, negative numbers and non-integers are not part of the trace. It also says the trace holds only the argument as passed and the returned list, so the request's "don't change the given array" can't be observed through these signals. I left the request's rules uninterpreted, including its contradictory ascending/descending condition. The `draft.yaml` used for anchoring is still in the workspace.
