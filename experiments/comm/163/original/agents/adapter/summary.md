I wrote `design.yaml`, `frame.md` and `requirements.yaml`, and `fcp lint` reports clean. Each cycle after the reset is one call of `generate_integers(a, b)`. The inputs `a` and `b` are 8 bits each (0 to 255), which covers the examples 2, 8, 10 and 14, the values next to them, and 0, which is just outside "positive". The returned list is on `result`, a list of at most 10 numbers from 0 to 255. That is longer than the request could ever need, so wrong answers such as all ten digits or extra numbers can still be recorded. The 2-bit `outcome` uses `raises: []` because the request names no exception: 0 means it returned a list that fits, 1 means it raised any exception or didn't finish, and 2 means it returned anything else. The `function` section declares the two `int` arguments and the list return. Its `scope` tries every value from 0 to 20, 60 random values and the example values for each argument. The one frame rule, F-EMPTY (`outcome != 0 -> len(result) == 0`), cites R-FR-1, which quotes `frame.md` line 43; `fcp anchor` filled in the line number from `draft.yaml`, which I left in the workspace. `frame.md` explains the calls, how lists are read, the signal widths and the outcome codes. It also says that negative arguments and arguments above 255 are not part of the trace, and it does not restate the request's rules.
