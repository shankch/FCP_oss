I wrote `design.yaml`, `frame.md` and `requirements.yaml`, and `fcp lint` reports `lint: clean`. Each cycle after the reset in cycle 0 is one call of `largest_prime_factor(n)`, with no state kept between calls. The argument `n` is a 16-bit input (0 to 65,535). That covers the values the request uses (2048 and 13195) and those just outside it (0, 1 and primes); 16 bits is a limit I picked, since the request gives no upper bound. The returned integer goes on a 16-bit output called `factor`, and a 2-bit `outcome` records how the call ended: 0 it returned an integer that fits, 1 it raised any exception or didn't finish, 2 it returned anything else. `raises` is `[]` because the request names no exception. The `function` section gives the name, the one `int` argument, `returns: {signal: factor, type: int}`, the outcome, and a scope of `n` from 0 to 2100 plus 2048, 13195 and 400 random values. `frame.md` gives the input and output tables and says negative arguments and values above 65,535 are not part of the trace. It has one frame rule, F-ZERO (`outcome != 0 -> factor == 0`). That rule cites R-FR-1 in `requirements.yaml`, a `definition` quoting `frame.md` line 40, which I got by running `fcp anchor` on `draft.yaml`; the draft is still in the workspace.
