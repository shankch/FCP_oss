I wrote `design.yaml`, `frame.md` and `requirements.yaml` for `eat(number, need, remaining)`, and `fcp lint` reports clean. Each cycle after the reset is one independent call. The three arguments are 10-bit unsigned inputs (0 to 1,023), which covers the allowed 0–1000 and 1001 just outside it. `frame.md` says negative arguments are not part of the trace. The returned value is a single list signal `result`: up to 3 elements of 11 bits each (0 to 2,047), so two arguments added together still fit, and so does a list one element longer than asked for. I used one list signal rather than one signal per element because the request returns a list, not a tuple. If a formalizer would rather write separate names than `result[0]` and `result[1]`, switching to two signals (`returns: {signals: [...]}`) is an easy change. The request names no exception, so `raises` is `[]` and the 2-bit `outcome` is 0 for a list that fits, 1 for any exception or no answer, and 2 for anything else. The single frame rule, F-EMPTY (`outcome != 0 -> len(result) == 0`), cites R-FR-1, a verbatim quote of `frame.md` that `fcp anchor` placed at line 46. The `scope` covers 0 to 12 for every argument (which includes the docstring's example values), 999, 1000 and 1001, and 40 random values each. Two things I could not check, because I didn't read the openfcp source outside the workspace: whether `type: list` also accepts a tuple as the return, and whether the scope combines the three arguments as a full product (about 125,000 calls). `draft.yaml`, the input to `fcp anchor`, is still in the workspace.
