I wrote `design.yaml` and `frame.md` for `eat(x, y, z)` and added the one frame requirement, R-FR-1, to `requirements.yaml`; `fcp lint` reports clean. Each call is one cycle, with cycle 0 as reset. The three integer arguments are 10-bit inputs named `x`, `y` and `z` as in the signature, which covers the allowed 0–1,000 plus 1,001 just outside it. `frame.md` notes that the docstring calls its variables `number`, `need` and `remaining` but does not say which parameter is which, leaving that to whoever formalizes the request. It also says negative arguments and anything above 1,023 are not part of the trace. The returned array is one list output, `result`: up to 3 elements, so a 3-element answer can be seen as wrong, and 11 bits each (0–2,047), enough for sums up to 1,001 + 1,001. Because the request names no exception, `raises` is `[]` and the 2-bit `outcome` is 0 for a list that fits, 1 for any exception or no answer, and 2 for anything else. The frame rule F-EMPTY says `result` is empty unless `outcome` is 0, and R-FR-1 quotes that line from `frame.md` (line 52, from `fcp anchor`). The scope tests 0–12 for each argument, which covers every docstring example, plus 999, 1,000, 1,001 and 20 random values. One untested assumption: I declared the return as a list rather than a pair (as `checkout` uses) because the request says the function returns an array; if the runner treats a returned tuple as "anything else", code returning `(total, left)` would get outcome 2.
